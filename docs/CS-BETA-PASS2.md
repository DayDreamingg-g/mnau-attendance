# Второй CS beta-pass · 14.09.2026

Изменения выполнены поверх текущей истории `E:\Repo\mnau-attendance`, ветка `main`, и применены к настоящей локальной PostgreSQL `mnau_attendance` через Docker. Пользовательский diff `src/app/login/page.tsx` сохранён отдельно, в наши commits не включён. Badge DEMO остаётся рядом с «ЕЛЕКТРОННИЙ ЖУРНАЛ».

## Найденные причины

1. Seed создавал специальности с ключами `:junior` и `:senior`, поэтому одно название КН соответствовало двум Specialty: группы 1–2 курса и группы 3–4 курса. Разные страницы выбирали разные записи. Исправлена модель данных и создание справочника, а не количество строк в UI.
2. `beta:prepare-cs` подготовил roster и аккаунты, но отдельный генератор CS-календаря не был применён. В основной БД отсутствовали `cs-calendar-*` Lesson. При этом beta scope уже скрывал прежние CS-only demo/schedule записи. Поэтому назначенные преподаватели и страницы групп показывали почти пустое расписание.
3. Заявленный 401 старосты КН 2/1 на исходной копии повторить не удалось: HTTP login уже возвращал 200. Найдена ненадёжность подготовки: существующие изменённые пароли/disabled state сохранялись. Целевой repair теперь явно обеспечивает согласованные bcrypt-пароли, активность, роли и назначения всех пяти старост; login/session проверяются через HTTP.
4. Навигация использовала широкие административные права как признак личного teacher workspace; `/sources` был доступен лишним ролям. Теперь авторизация отделена от уместности личных разделов, а Sources защищён сервером.
5. Формы управления студентами выводились ниже таблицы; аккаунт, профиль и перевод смешивались. Reports требовал preview и мог сохранять пустую выборку; provenance не отделял ручные записи от DOCX. Дополнительно браузер выявил несовпадение faculty по умолчанию с единственной beta-specialty в отчётах — исправлено.
6. `teacher@test.com` не найден ни в качестве текущего beta Teacher, ни как User в рабочей БД. Hardcoded/defaultValue этого email в login отсутствует. Браузерная форма входа пуста; источник прежнего автозаполнения Chrome доказать нельзя.

## Применённая стратегия

Перед repair выполнен `pg_dump -Fc`. Локальная копия: `runtime/backups/mnau-cs-before-repair.dump`, 1 080 297 байт; путь игнорируется Git. Секреты и dump в commits не добавлены.

Новая схема БД не требовалась: текущие четыре Prisma migrations применены, pending migrations нет. Данные меняет `npm run beta:repair-cs`: DEMO-only, production lock, проверка имени БД и существующей подготовки, PostgreSQL advisory lock, блокировки групп, одна транзакция. Normal seed внутри repair не вызывается.

Repair объединяет Specialty, сохраняет исходные snapshots в provenance/AuditLog и aliases старых URL; привязывает реальные группы по именам из общего справочника. Восстанавливает только отсутствующие официальные import rows. Повторный запуск не переводит обратно и не разархивирует законно изменённых студентов. Восстановление beta-доступов является намеренным действием repair, а не фоновым процессом.

PDF извлечены заново с учётом колонок, линий таблицы, номера пары, merged/shared cells и половин. Страницы и увеличенные фрагменты всех четырёх PDF просмотрены визуально. Сохранены raw text, page, cell/pair bbox, исходное написание преподавателя и SHA-256. Build сверяет hashes PDF и полноту календаря. Числа ниже получены из extraction, не заданы как ожидаемое расписание вручную.

Старые CS-only generated занятия отменяются с сохранением записей; у общих занятий с другими направлениями отделяется только связь КН. Ручная история сопоставляется по дате, паре, группам, предмету и преподавателю. При неоднозначности вся транзакция откатывается. Старые audit rows генератора demo, оставшиеся после удаления synthetic students, сохранены; их наличие без Attendance/submission не считается ручным журналом. Будущие пустые roster пересобираются; прошлые snapshots, отметки и подтверждения сохраняются. Изменения roster обновляют версии журналов.

Первый успешный repair создал 1410 Lesson и вывел из активного CS-календаря 1273 прежних generated занятия. Повторный repair: created=0, updated=0, retired=0, cleaned=0, imported=0. Тест проверяет сохранение ручной отметки и полный rollback при неоднозначном сопоставлении.

## UX и доступ

- Добавление студента и управление строкой открываются в центрированном native dialog с overlay, Escape, закрытием снаружи, возвратом фокуса и блокировкой прокрутки фона. Нет формы под длинной таблицей.
- Профиль, перевод, архивирование и аккаунт разделены. Профиль не содержит group selector. Success диалог аккаунта показывает email/пароль однократно и кнопки копирования; закрытие очищает пароль.
- Архив скрыт из активного списка по умолчанию. Окончательное удаление ограничено ADMIN/DEVELOPER, требует отдельного подтверждения, запрещено при официальном импорте/учебной истории/самостоятельной истории User.
- Административные действия зависят от роли выбранного пользователя. По умолчанию dropdown групп содержит только пять КН; переключатель «Увесь факультет» сохраняет полный backend access менеджеров.
- «Мої заняття» требует реального Teacher profile. Teacher и Starosta не получают общий `/sources`; телефоны не отправляются Teacher сервером.
- Sources различает IMPORT/MANUAL/TRANSFER/ARCHIVE, actor, время, reason и старую/новую группу. Ручная запись не приписывается DOCX.
- Reports: «Створити звіт» → «Створення...» → «Звіт створено», строка обновляется на той же странице. Preview блок убран; API preview сохранён для существующих программных потребителей. Нулевая выборка возвращает 422 без Report/PDF/CSV. Действия сохранённой строки: «Відкрити», PDF, CSV. Фильтры перестраиваются на узком экране.
- Профиль реального студента показывает один контекст отсутствия подтверждённых отметок; техническая метка заменена данными об официальном списке или ручном профиле.

Формула, HV, пороги до округления, raw totals, draft/confirm, optimistic concurrency, transaction save и AuditLog сохранены и покрыты тестами.
